== Какие выводы?

image::jacoco-branch-50.png[]

* Покрытие ветвей (C1) не зависит от их «длины»: каждая точка ветвления имеет одинаковый вес при расчёте процента.
* Проценты получаются *более пессимистичными*, но для проекта это полезнее (скоро разберём почему).
* Мой совет: переходите с покрытия строк и инструкций на покрытие ветвей *прямо сейчас*.

Цикломатическая сложность +
(здесь — 3) — это

* *верхняя граница* числа тестовых случаев, необходимых для полного покрытия ветвей +
(здесь — 2, например: `AC`, `BD`)
* *нижняя граница* числа путей в графе потока управления +
(здесь — 4: `AC`, `AD`, `BC`, `BD`)

== Метрика «цикломатическая сложность»

* Предложена Томасом Маккейбом в 1976 году.
* *Очень легко вычисляется для любого языка программирования*: достаточно простейшего лексического и синтаксического анализа.
А вот для подсчёта реальных путей выполнения нужно различать возможные и невозможные пути.
* Аддитивна: можно посчитать CC всего проекта.
* Это «примерно столько, сколько нужно юнит-тестов».

== Какое значение CC допустимо?

[%step]
* Классификация Маккейба для одной процедуры (слайды 2008 года → Википедия):
** 1–10: простая процедура, низкий риск
** 11–20: более сложная, умеренный риск
** 21–50: сложная, высокий риск
** > 50: нетестируемый код, очень высокий риск
* Моя классификация (Иван Пономарёв, 2026):
** 1–15: нормально
** > 15: бардак; если код не сгенерирован детерминированно — рефакторить

== Какие выводы?

* Цикломатическая сложность легко вычисляется и доступна для большинства языков.
* Установите ограничение CC ≤ 15 на метод: это поможет сократить число багов и выявить проблемные места в коде.

== Подоходный налог в вымышленной стране

[cols="55a,45a"]
|===
|
* Необлагаемый минимум — €10000 в год.
* Но при годовом доходе свыше €25000 каждый евро превышения уменьшает необлагаемый минимум на €0,5.
* С облагаемой суммы взимается налог 25% +
(доход минус необлагаемый минимум).
* Если облагаемая сумма превышает €100000, с превышения взимается 35%.

== Какие выводы?

[%step]
* Завышенный порог покрытия не приводит к реальному улучшению кодовой базы.
* Мой вариант: 75% — наибольший разумный порог для покрытия ветвей.
* Измеряйте покрытие юнит-тестами и интеграционными тестами отдельно, с отдельными порогами. Так картина будет точнее, чем с завышенным «общим покрытием».

== Мутационное тестирование (например, PITest для Java)

* Запускаем тесты на автоматически изменённых (мутировавших) версиях кода
* На изменённом коде тесты должны падать!
Если тест упал — мутант *убит* (это хорошо). Если нет — мутант *выжил* (значит, в тесте есть изъян!).

== Примеры мутаций

[cols="65a,35a"]
|===
|
** Возврат константы вместо вычисленного результата
** Удаление вызова метода
** Логическое подвыражение → константа `true` или `false`
** `+` → `-`, `*` → `/` и т. д.
** `>` → `>=`, `==`, `<=` и т. д.
** Переменная → другая переменная совместимого типа из той же области видимости
** И так далее

== Эквивалентные мутации

При случайной генерации мутаций изменённый код может оказаться семантически эквивалентным исходному:

* `a + b` -> `b + a`
* `if (x > y) return x else return y` -> `if (x >= y) return x else return y`

== Мутационное покрытие налогового калькулятора

image::pitest-tax.png[]

== Мутационное покрытие налогового калькулятора

[source,java]
----
long tax;
long allowance = 10000;                     // 10000 → 10001
if (income > 25000) {                       // > → >=, 25000 → 25001
    long reduction = (income - 25000) / 2;  // 25000 → 25001
    allowance = Math.max(0, allowance - reduction);  // 25000 → 1
}
long taxableIncome = Math.max(0, income - allowance); //max → argument, 0 → 1
if (taxableIncome <= 100000) {              // < → <=, 100000 → 100001
    tax = Math.round(taxableIncome * .25);
} else {
    tax = Math.round(100000 * .25);
    long remaining = taxableIncome - 100000; //100000 → 100001
    tax = tax + Math.round(remaining * .35);
}
return tax;
----

== Что нам показало мутационное тестирование?

* Стоит добавить тест для дохода ниже необлагаемого минимума, а также тесты на граничные значения.
* Мутации `> → >=` — *эквивалентные*: сумма налога — непрерывная функция. Это *ложные срабатывания*.

== Практические проблемы

* На реальном коде *МЕДЛЕННО*: 2 минуты → 40 минут.
* *Эквивалентные мутации* дают ложные сообщения о «недостатках» тестов.

* Современные инструменты борются с обеими проблемами. Борьба продолжается +
(см., например, https://archive.fosdem.org/2024/schedule/event/fosdem-2024-2486-how-mutation-testing-got-practical/[Jan-Jelle Kester. Stryker: How mutation testing got practical], FOSDEM 2024)
* Вы сами можете внести вклад: https://github.com/jacoco/jacoco/issues/2190[JaCoCo #2190: Boundary-value coverage: flag numeric comparisons whose boundary (left == right) is never tested]

== Какие выводы?

* Для критически важного кода мутационное тестирование даёт высокую уверенность: оно оценивает качество самих тестов.
* Результаты нужно интерпретировать осторожно: среди реальных проблем встречаются ложные срабатывания.
* Мутационное тестирование — это *медленно*.
* На практике его всё ещё считают непрактичным и применяют довольно редко.

== Итоги

* Сегодня и *код, и тесты обходятся дёшево*, +
а метрика покрытия кода *раздута и обесценена*.

* Вернём ей смысл: будем измерять осмысленно +
и откажемся от высоких, но бессмысленных цифр.

== Мои практические рекомендации

[%step]
* Откажитесь от C0 — покрытия строк. *Переходите на C1 — покрытие ветвей — уже сегодня.* Проценты будут ниже, но честнее.
* Ограничьте *цикломатическую сложность значением 15* на метод во всём проекте.
* Не гонитесь за красивыми порогами покрытия от 80% и выше. Практичный ориентир — *60–75%*.
* Измеряйте покрытие юнит-тестами и интеграционными тестами *отдельно*, с отдельными порогами.
* Смотрите на *отчёт о покрытии, а не только на процент*.
Ищите потенциально опасные участки; для критичного кода применяйте фаззинг и/или мутационное тестирование.
* Следите за *современными инструментами*.
Инструменты для C2 и мутационного покрытия развиваются, но *многое ещё впереди*.
